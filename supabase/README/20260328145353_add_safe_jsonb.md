## Migration Purpose

> Due to security concerns about potential script or HTML injection in JSONB, I introduced a validation layer on top of the JSONB type called safe_jsonb.

## Validation Function

```
create or replace function is_safe_jsonb(data jsonb)
returns bool
language sql
as $$
    select not exists (
        select 1
        from jsonb_array_elements_text(
            jsonb_path_query_array(data, 'strict $.** ? (@.type() == "string")')
        ) as val
        where
            val ~* '</?[a-z][^>]*>'
    )
$$;
```

### `jsonb_path_query_array(data, 'strict $.** ? (@.type() == "string")')`

This is the heart of the recursion. It returns a JSONB array of every string value found anywhere in the document, no matter how deep.

Breaking down the JSONPath expression:

- `$` — the root of the document
- `.**` — recursively descend through all nested levels
- `? (@.type() == "string")` — filter, keeping only string-type values

#### example

```
<!-- Input -->
'{
   "user": {
     "comments": ["<html/>inject"],
     "message": "some message",
     "json": {"hello": "<h1>hi</h1>", "array": ["deep nested array"]}
   },
}'

<!-- Output -->
["deep nested array","<h1>hi</h1>","some message","<html/>inject"]
```

### `jsonb_array_elements_text(...)`

Unpacks that JSONB array into individual rows of plain text — this strips the JSON quotes so "hello" becomes hello.

### `~*`

Case-insensitive regex match. This means <SCRIPT/>, <Script/>, and <script/> are all caught.

### `'</?[a-z][^>]*>'`

Matches all

- <script ...> or </script>
- any opening HTML tag like <h1>, <a ...>
- any closing tag like </h1>, </a>

### `not exists (...)`

- Returns true (safe) only if none of the string values match any prohibited pattern.
- The NOT EXISTS subquery already short-circuits. PostgreSQL stops scanning the moment it finds the first matching row and immediately returns false.

### `set search_path = ''`

[link](https://supabase.com/docs/guides/database/database-advisors?queryGroups=lint&lint=0011_function_search_path_mutable)

In PostgreSQL, the search_path determines the order in which schemas are searched to find unqualified objects (like tables, functions, etc.).
When a function has a mutable (unset) search_path, an attacker can exploit it like this:

1. You write a function that calls jsonb_path_query_array

```
create function is_safe_jsonb(data jsonb)
returns bool
language sql
as $$
    -- PostgreSQL resolves jsonb_path_query_array via search_path
    select not exists (...)
$$;
```

2. An attacker creates a malicious schema and a fake function with the same name

```
create schema malicious;

create function malicious.jsonb_path_query_array(jsonb, jsonpath)
returns jsonb
language sql
as $$
    -- silently steal the data or always return empty to bypass the check
    insert into malicious.stolen_data values ($1);
    select '[]'::jsonb;
$$;
```

3. The attacker manipulates the search_path to put their schema first

```
set search_path = malicious, public;
```

4. Now when is_safe_jsonb runs, it finds malicious.jsonb_path_query_array before the real built-in one — and your validation is completely bypassed.
