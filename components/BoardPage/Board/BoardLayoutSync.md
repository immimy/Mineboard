# BoardLayoutSync notes

Purpose: Wait for a board's previous layout saves to settle before mounting its query and displaying the board as ready.

- **Navigation does not stop layout saving.** A debounced or running save can outlive the board UI. Revisiting too early could initialize the board from an older Apollo cache layout while the previous worker still owns unfinished work.
- **The shared provider tracks unfinished work by board ID.** `BoardLayoutSync` checks that provider before rendering `BoardContainer`. Waiting flushes queued work and follows the entire save cycle, including additional queued saves, rather than waiting for only one request.
- **Support both fresh mounts and preserved instances.** With `cacheComponents: true`, Next.js can keep recently visited routes hidden using Activity, preserving state and DOM. Preservation is not permanent: routes can be evicted, so a revisit can also create a new component. See the [Next.js preservation guide](https://nextjs.org/docs/app/guides/preserving-ui-state).
- **A fresh mount checks before rendering the board.** The initial loading state comes from the provider. If that board has no unfinished save, `BoardContainer` can render immediately.
- **A preserved gate must check again on reappearance.** Activity cleans up effects when hidden and runs them again when visible. Cleanup resets loading and clears errors; `useLayoutEffect` then checks the provider before the next paint. The state initializer alone cannot handle reappearance because preserved state is reused.
- **The key separates board identities.** `key={boardId}` ensures a changed board ID gets fresh gate state instead of inheriting another board's readiness. Cleanup and effect setup happen after rendering, so they cannot replace this initial-state protection. The key does not guarantee a remount on every revisit to the same board.
- **Ignore obsolete wait callbacks.** Cleanup sets the effect-local `active` flag to `false`, preventing its promise callbacks from changing state after hiding, unmounting, or an effect restart. This does not cancel the background save and is separate from the provider registration's `active` field.
- **Ordinary drags keep the board visible.** The gate checks on entry or reappearance; it does not subscribe to every save. Loading remains visible only while previous work is unfinished. A reappearance with nothing pending clears loading before paint.
- **A handled save failure still releases the gate.** The worker reports save errors and handles recovery. Once its work has settled, the board can read the confirmed Apollo cache normally. The gate's error UI is reserved for unexpected coordination failures.
- **Preserving the gate does not preserve the whole board UI.** Resetting loading removes the `BoardContainer` subtree. This intentionally favors checking pending work before recreating the query and drag area over retaining their local UI state.
- **Keep the responsibilities separate.** This component coordinates board entry. The provider coordinates mutations with layout saves, and each dialog owns its submitting state and dismissal prevention. Activity preservation does not replace Apollo's server-data cache or synchronize writes by itself.
